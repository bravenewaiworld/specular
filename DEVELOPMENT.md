# Specular Frontend Development Guide

## Running Specular

- **On the desktop.** The desktop build runs Specular in a 1024×768 window, against a data folder on your PC that stands in for the SD card (its argument: `specular <folder>`; default `./sdcard`). Sound is real. Everything else is simulated:
  - The battery drains slowly, from 80 % or `SPECULAR_BATTERY`.
  - The last run ended cleanly, unless `SPECULAR_LAST_SHUTDOWN=<word>` says what Crystaline OS would have recorded: `battery-empty`, `unexpected`, or any other word (reported as `unexpected`). Its notice shows at every start while it is set.
  - Hardware actions are printed instead of performed.
  - WiFi and Bluetooth follow a recorded or hand-written scenario (see Wireless traces and scenarios).
  - The installer runs from the SD card, with one backup, a previous version and three update files (a newer one, an older one, and one that can't be installed). It can be made to run from the internal storage, where Restore prepares the card (`SPECULAR_INSTALL_INSTALLED`); to have a prepared restore waiting on the card, asked about at start-up (`SPECULAR_INSTALL_PENDING`); to fail (`SPECULAR_INSTALL_FAILS`); or to look like a task was left running (`SPECULAR_INSTALL_RUNNING=<install|restore|update|activate>`).
  - File transfer prints the `sv` commands it stands for (`simulated: sv up webdav`), and starts in half a second; `SPECULAR_TRANSFER_FAILS` makes it fail as when the server can't listen. The USB cable's address is the default scenario's `usb0`.
  - The SD card is always in and writable, unless driven (see Driving the SD card's states).
  - SSH is a release system's: off, with no keys; importing finds two. `SPECULAR_SSH=no-keys` makes the import fail as without `authorized_keys`; `SPECULAR_SSH=development` makes it a development system's (no switch, only a note).
  - The CPU has the Brick's speed steps (408–2000 MHz). It prints `simulated: CPU profile balanced` at start-up, then each minimum it is given (`simulated: CPU minimum 1800 MHz`, `simulated: CPU minimum the system's default`).
  - The time zone starts at UTC, whatever the PC's, and is kept in memory (lost at quit). The zones are the PC's (`/usr/share/zoneinfo`). Once allowed, the lookup is a real request over the PC's network, made when the scenario's WiFi connects (the built-in scenario connects when "Home" is joined). `SPECULAR_TIMEZONE_LOOKUP=<answer>` answers it instead, without the network: a zone (`Europe/Paris`), an alias (`US/Eastern`), one no system has (`Mars/Olympus_Mons`: refused), or empty (a blank answer: refused). To replay a device's lookup, give it the answer the device logged, without the quotes.
- **Cores** are loaded from `SPECULAR_CORES`, or else from `cores/` next to the binary.
- **Cores the user adds** go in the data folder's `cores/`: `<name>_libretro.so` beside its `<name>_libretro.info`. To try one, copy a host-built core under a name of its own with an `.info` naming the systems it plays: `cp target/cores/host/mgba_libretro.so sdcard/cores/mine_libretro.so`, then `sdcard/cores/mine_libretro.info` holding `corename = "Mine"` and `database = "Nintendo - Game Boy Advance"` (or a real `.info` from libretro-core-info, renamed). The GBA then has two cores: its game and system settings get a "Core" row. Its options are learned the first time it plays a game; delete `cache/cores/` to learn them again.
- **BIOS files** go in the data folder's `bios/`. PS1 games run without one, on SwanStation's built-in OpenBIOS (some games don't: a game OpenBIOS halts is quit, saying which files to add); Famicom Disk System games need `disksys.rom`. The log says which files were looked for.
- **Keyboard as gamepad:**
  - Arrows: D-pad. X/Z/S/A: A/B/X/Y.
  - Q/W: L1/R1. 1/2: L2/R2.
  - Enter: Start. Tab: Select. Esc: Menu.
  - −/=: volume. P: power button.
  - H: plugs headphones into the jack, or unplugs them (simulated).
- **On a device.** Specular can be run once in the foreground, with its output on your terminal. Or it can replace the installed one and be restarted. See the Crystaline OS development guide.

## Seeing what it does

- **Log.** Messages go to stderr, prefixed by area (`game:`, `sound:`, `transfer:`, `ssh:`, `art:`, `saves:`, `settings:`, `input:`, `install:`, `core:`, `cores:`, `fonts:`, `rumble:`, `effects:`, `ui:`, `power:`, `cpu:`, …). On a device they end up in the system log.
  - `fonts:` says at start-up which of the SD card's fonts are used, and why any aren't.
  - `input:` says at start-up which headphone jack device is followed, or that none was found; then each plug and unplug. `sound:` has each output switch and each level set (`sound: Headphones volume 10`, with `(muted)` while muted). The speaker's and the headphones' levels are set whenever they change or the sound is muted or unmuted, whichever plays, and not when the jack changes (the kernel switches between them); a Bluetooth output's is set as sound moves to it.
  - `rumble:` says at start-up which gamepad rumbles (`rumble: TRIMUI Player1 (/dev/input/event3)`), or that none offers it yet (it is looked for again when something next rumbles), or that the device has none; then a gamepad gone, and errors (each once, until another comes, or `rumble: working again`). `game: the core uses rumble` says the running core asked for it (mGBA asks once its game first rumbles). On the desktop, each change of the motors is printed (`simulated: rumble strong 65535 weak 65535`).
  - `effects:` has a line each time a lights or rumble effect starts (`effects: low battery`, `effects: save flash`, `effects: rumble following the sound`, the last once per stretch of play, until the game pauses). On the desktop, saving a state from the in-game menu flashes the light bar, and `SPECULAR_BATTERY=16` starts the simulated battery a minute from low.
  - `cores:` names each core found on the card, the systems it plays, its file and whether its options are learned, and each file in `cores/` not used, with why (at start-up and whenever that changes); then `cores: learned <core>'s options` at a core's first game. With Developer details, Settings → Cores lists the same.
  - `settings:` names each settings file loaded with its values, each value ignored (its file, key and why), and each file under `games/` for no game in the library.
  - `library:` counts the games of each system no core plays, whenever that changes; `guides:` names each `README.txt` written (only when its text changed). What needs attention on home (`App::problems`) is worked out from what these lines report, so each problem shown has its log line; to see one on the desktop, put a `.sfc` in the data folder's `roms/`, a text file in `fonts/`, or a damaged file in `config/v0/systems/` (it becomes `.bad`).
  - `power:` says at start-up how the last run ended, as the system recorded it (`power: the last run didn't end cleanly: "unexpected\n", reported as Unexpected`, with `a word Specular doesn't know` for another word), or that there is none (`power: no shutdown record: the last run ended cleanly`); then when a PC connects over the USB network link (`power: a PC is connected over USB (usb0, 192.168.7.2): no idle sleep until it goes`) and when the link goes. The device doesn't sleep by itself in between; working over WiFi alone, set "Sleep after" to Never.
  - `cpu:` has the CPU's speed steps at start-up (or why no minimum can be set), then at each launch the minimum the game starts with and why (its core's start level, or `power.cpu_min` and the file setting it), each step up with why (2 frames that missed their refresh, how far apart, at what minimum), the default set while the game is paused and as it ends, and, once per game, that frames still miss their refresh at the top step. On the Brick, each `brick-power` run is logged too, with its exit status, output and errors (`cpu: /usr/sbin/brick-power cpu-min 2000: exit status: 0, stdout "2000", stderr ""`).
  - Each launch: `game:` says when the autosave is written, and where that comes from (`game: SwanStation autosaves only when play stops (game.autosave = "core default", its default)`, `game: mGBA autosaves every 10 s of play, and when play stops (game.autosave = "every 10 s", in systems/gba.json)`), and when the game's first frame came (in ms after the launch), and how much longer the splash hides it (the splash shows for at least 1 s).
  - A zipped game: `game:` says what was unzipped, how big and how fast, then the path the core is given (a link named like the zip, with the game's extension, to the unzipped game in memory), or why that link couldn't be made.
  - A game on several discs: `game:` gives what the core says about them at launch (how many, their labels, the one in), the disc it was told to start on (the autosave's), each change of disc or why one failed, and a state loaded that was made on another disc.
  - At launch, `game:` gives the core's options as given (`game: mGBA's options: …`), those it doesn't take, and how what it declares differs from its list in `data/cores/` (to be expected only on another processor); then each option changed mid-game, with its old and new values.
  - A PS1 game OpenBIOS halts: `core: SwanStation error: [DoEXP2Access] OpenBIOS halted the game (POST 09)` (POST 0F is OpenBIOS's fatal error: the boot file couldn't be loaded, or a CD read failed; any other, a BIOS function or patch it lacks), then `game: SwanStation says its built-in BIOS halted the game, at frame 462; its autosave … is removed, and no longer written`, and `game: stopped: <the notice>`. SwanStation's `No BIOS image found for <region> region`, earlier, says it fell back to OpenBIOS.
  - The running core's own messages come as `core: <core> <level>: <message>` (e.g. `core: mGBA warn: …`), without its debug ones and at most 30 a second; `core: <core>: N more messages dropped` says how many were left out.
  - `art:` has a line for each game identified by fuzzy name, and for each it couldn't identify, with the reason (e.g. several similar names, or only sequels'), plus disc serials that can't be read or aren't in the table. Each time the art worker runs out of work it adds how many games it identified by each method, and how many pictures of each kind it downloaded and how many games no source had one for (`art: downloaded 4 pictures: 3 title, 1 boxart; none to be had for 2 games: 2 title`). Identifications are cached, so delete `cache/identify/` to see them again. Each game quit logs the frame kept as where it was left off: its file, size and how long storing it took (`art: left off: …/cache/art/left-off/gba/Golden Sun.png (240×160 from 240×160, 31 KB) in 9 ms`). At start-up, the number of entries moved from an older `cache/art/` (box art only) into `cache/art/boxart/` is logged.
  - `transfer:` has every command file transfer runs on the device, with its exit status and output (`transfer: /usr/bin/sv up webdav: exit status: 0, stdout "", stderr ""`), `transfer: port 80 takes connections` once started, and why a start or stop failed. A stop is logged at every start-up and quit of Specular. `ssh:` has each `brick-ssh` run the same way, then the result the app got (`ssh: Status: Ok(SshStatus { switchable: true, on: false, keys: 0 })`).
- **Time zone.** `timezone:` gives the zone in effect and how many zones there are at start-up, each lookup's answer as it came (`timezone: lookup: http://ipinfo.io/timezone answered "America/Toronto\n"`) or why there is none, and each zone set or refused with the system's message.
- **Checking the time zone on the Brick.** Run Specular in the foreground to see its log, with an SSH session. Start with neither `time.zone` nor `time.zone_lookup_allowed` in the card's `config/v0/specular.json` and `brick-timezone set UTC`.
  1. Open Wi-Fi and join a network: once connected, "Look up the time zone?" opens. Allow: the log has `timezone: lookup: … answered "<zone>"` and `timezone: set <zone>`, the clock in the status bar changes at once, and `brick-timezone get` prints the zone. Settings → Time zone shows "Set: Automatically" and the zone.
  2. Turn WiFi off and on (or leave and rejoin): one lookup per connection, none on signal readings.
  3. Restart Specular (as in the Crystaline OS development guide), then the device: the zone, the clock and "Automatically" are kept, and the question isn't asked again.
  4. Settings → Time zone → Zone → an area → a zone: "By hand", `brick-timezone get` prints it, and the clock changes at once. Rejoin WiFi: no lookup.
  5. Delete `time.zone` and `time.zone_lookup_allowed` from `specular.json`, restart Specular and rejoin WiFi (if it doesn't reconnect by itself); at the question, B (or "Choose it myself"): "By hand", the zone stays, and joining again asks nothing.
  6. With no internet behind the network, a lookup logs why it failed and changes nothing.
- **Wireless trace.** Every call to and event from the WiFi, Bluetooth and SD card services is logged with a timestamp. Passwords are redacted. The trace is always on.
- **Frame statistics** (a developer setting): fps, the core's median and 95th-percentile time per frame, how much sound is queued, the rumble's strength while it rumbles (the game's and the effects' together, after the "Rumble" setting), and the CPU's minimum speed while one is set (`CPU ≥ 1800 MHz`), drawn over the game on two lines (the sound, rumble and CPU on the second). Also, at the bottom right (on every screen, and over a game), the times between the UI's frames while something animates: how many, how many came late (more than 1.5 refreshes after the one before, so a refresh showed a frame twice), how many extra (under half a refresh: two frames for one refresh, one never shown) and the longest; under them, the last animation's CPU time per frame. Each animation that ends also logs two lines:
  - `ui: 9 frame times: median 16.6 ms, longest 17.0 ms; 0 late, 0 extra`
  - `ui: CPU a frame: median 4.1 ms, 2.9 ms of it drawing (longest 6.0, 4.2); 4 row slots changed; 23 slots, 18 with rows, 6 on screen`: the UI thread's CPU time from one frame to the next, and the part spent drawing (Slint walking the scene, FemtoVG building paths and glyph runs, the GL calls; presenting the frame, the buffer swap, isn't counted in it). Then, over the animation (from the frame before it), the row slots given new data. Last, the row slots now: how many, how many hold rows (those near the view), and how many of those are on screen.
- **Checking the menus' frame pacing on the Brick.** Turn on Developer details, then Frame statistics, and run Specular in the foreground to see its log. Scroll a long list, hold a direction, open and close screens and the in-game menu, and launch a game (its cover zooms into it): each `ui:` line should show a median of about 16.6 ms (60.2 Hz), with a frame or two late per short animation and up to about a dozen over a 6 s held scroll (measured 2026-10-19). Zooming into and out of a game runs at half rate (a known problem, see ROADMAP.md). Then leave it idle: no `ui:` lines, and `top` shows Specular at about 0.5 % CPU. To see that nothing is presented while idle, `strace -f -p <pid>` for 10 s should show no ioctl on `/dev/fb0` (`FBIO_WAITFORVSYNC`) nor on the GPU's `/dev/dri/renderD128` (where buffer swaps go); turn Frame statistics off first, as their timer wakes the loop once a second. Every frame late (a median near 33 ms) means each wait for the vsync ends a refresh late (a kernel whose `FBIO_WAITFORVSYNC` takes the framebuffer lock; see docs/brick.md). While a game runs, show the volume gauge or a toast over it: the game's fps should stay at 60. `s1_slint 20 --continuous --vsync` checks the same without Specular, and should show 60.2 frames/s, 0 late and about 1 ms in the swap (against most of a refresh without `--vsync`); `s1_slint 20 --idle --vsync` should show no frames and about 0.5 % CPU.
- **Checking the CPU minimum on the Brick.** Turn on Developer details, then Frame statistics, and run Specular in the foreground to see its log, with an SSH session. At start-up the log has `cpu: speed steps [408, 600, 816, 1008, 1200, 1416, 1608, 1800, 2000] MHz`, after `brick-power profile balanced`. Start a PS1 game (Symphony of the Night or Metal Gear Solid): `cpu: SwanStation starts with a minimum of 1800 MHz …`, and the statistics show `CPU ≥ 1800 MHz` and should hold 60 fps, past the game's openings. `brick-power` (no arguments) shows `cpu-min   1800` and the speed now. Any step up comes with a `cpu: minimum …` line saying why, and the minimum never comes down while the game plays. Open the game's menu: `cpu: minimum the system's default (while the game is paused)` and `cpu-min   default`; resume, and the game's minimum comes back; quit, and it goes back to the default. A GBA game logs `mGBA starts with a minimum of the system's default` and sets none unless its frames miss (two misses within a second then set 1200 MHz). To compare by hand, put `"power.cpu_min": "off"` (the governor alone) or a speed such as `"2000"` in the card's `config/v0/systems/ps1.json` (or one game's file under `games/`) and launch again; the launch line names the file. Frames that still miss at the top step log `cpu: … the top step: there is no faster one to set`, once a game; `brick-power`'s status then says whether a heat limit holds the CPU below it (`thermal limit step` above 0).
- **Checking the speaker's and headphones' volume on the Brick.** Run Specular in the foreground to see its log, with wired headphones and a Bluetooth headset at hand, and an SSH session for `amixer`. A level `L` is the control's step `159 − (20 − L) × 8/3`, rounded (20 → 159, 12 → 138, 10 → 132, 1 → 108), and 0 → 0.
  1. Start-up: the log has `input: headphone jack: audiocodec sunxi Audio Jack`, then `sound: Speaker volume S` and `sound: Headphones volume H` with the settings' levels. `amixer -c audiocodec cget name='Speaker Playback Volume'` and `… name='Headphone Playback Volume'` show their steps (e.g. `: values=138` for level 12). (An older OS has `DAC volume` instead, in `amixer -c audiocodec controls`; there each set fails with `hardware:` in the log.) `… cget name='Headphone Jack'` says `off` with the jack empty.
  2. With the jack empty and Interface sounds on, in Settings → Sound, set "Headphone volume" to 20 and then 0: the Headphone control follows (159, then 0), the Speaker one doesn't, and the ticks from the speaker keep their loudness.
  3. Set "Headphone volume" back to something comfortable and start a game with steady sound. The volume keys show the gauge without the headphones mark and change the speaker's loudness and only the Speaker control. Plug the headphones in: `input: headphones plugged in`, `sound: output Headphones`, and no `sound: … volume` line. The speaker goes silent and the headphones play at their own level from the first moment (no burst at the speaker's level); `Headphone Jack` says `on`. The volume keys now show the headphones mark and change only the Headphone control. Unplug: `unplugged`, `sound: output Speaker`, the speaker plays at its level again, and the keys change only the Speaker control. Repeat both with the game's menu open, then go back to the game: the right output plays at its level.
  4. Flip the FN switch to mute: both controls read 0 (`sound: Speaker volume 0 (muted)`, `sound: Headphones volume 0 (muted)`). Plugging in or out stays silent. Unmute: both go back to their steps.
  5. Connect the Bluetooth headset: `sound: output Bluetooth(…)`, `sound: Bluetooth(…) volume B`, and the game's sound moves to it. The volume keys show the Bluetooth mark and change the headset's loudness and `amixer -D bluealsa:DEV=<address> cget name='A2DP Playback Volume'` (B × 5 %), while neither codec control changes. Plugging wired headphones in and out meanwhile leaves the sound on the headset at its volume and the codec controls as they were. Disconnect the headset: sound returns to the jack or the speaker, at that output's level.
- **Checking file transfer on the Brick.** Run Specular in the foreground to see its log, with WiFi on Auto, a PC on the same network, and a USB cable at hand. Find the device's address on the Wi-Fi screen. Without a browser, `curl -T <file> http://<address>/<name>` uploads, `curl -o <file> http://<address>/<name>` downloads and `curl -X DELETE http://<address>/<name>` deletes. Specular checks that the server has started by connecting to 127.0.0.1:80, so the loopback interface must be up (`ip addr show lo`); without it, the start fails after 5 s although the server answers from the PC.
  1. Start-up: the log has `transfer: /usr/bin/sv -v down webdav: exit status: 0, stdout "ok: down: webdav: …"`.
  2. Open Settings → File transfer: `transfer: /usr/bin/sv up webdav: …`, then `transfer: port 80 takes connections`, and WiFi comes on (`wireless wifi … call {"Power":true}`). The screen shows the warning and `Wi-Fi  http://<address>/` once connected. Connect the USB cable to the PC: within a few seconds a `USB cable  http://192.168.7.2/` row appears.
  3. On the PC, open `http://<address>/` in a browser and upload a small game into Games → a system's folder; it shows in Specular's library. Do the same over `http://192.168.7.2/`.
  4. Leave the screen with B: `transfer: /usr/bin/sv -v down webdav: … "ok: down: webdav: …"`. From the PC, `curl -m 5 http://<address>/` fails (connection refused); on the device `sv status webdav` says `down` and `netstat -ltn` lists nothing on port 80. Open the screen again, then press Menu: the same stop.
  5. Sleep with it open: open the screen and wait past "Sleep after": it doesn't sleep. Tap the power button: the stop comes before `sleepnow` runs (port 80 closed, as in 4). Wake: `sv up webdav` and `port 80 takes connections` again, and the browser page loads again after a reload.
  6. A crash with it open: open the screen, then `kill -9` Specular (the service manager starts it again). At its start-up the stop of step 1 runs, and port 80 is closed.
  7. A failed start: on a development system with its developer layer, `mv /usr/bin/dufs /usr/bin/dufs.off`, then open the screen. After 5 s it says "File transfer didn't start: " with `sv status webdav`'s line and the service's last log lines, and offers Try again; `sv status webdav` says `down`. Put dufs back and press Try again: it starts.
  8. With the screen open, take the SD card out: the system's message about the card, and the log has the stop. Put it back: it starts again.
- **Checking the SD card on the Brick.** Run Specular in the foreground to see its log, with two FAT32 cards with games (A and B), one of them with a write-protect switch if at hand, and an SSH session for `cat /run/card/state` and `logread -f -e mount-card`. Every state Specular sees is a `wireless card … event {…}` line; a recheck is `wireless card … call "Recheck"`.
  1. In the library, take card A out: the message (line 2 of the state file) replaces the systems, within a second of `mount-card` logging `absent`; a system's game list open at the time closes to home. Put it back: "Checking…" (the system's words), then the library again; the log has `settings: loaded …` and a new scan. Copy a game onto the card over File transfer: it appears (the new watch works).
  2. Insert card B: its library and its settings (e.g. another brightness) replace A's.
  3. Mid-game (a GBA game first; PS1 disc games, which read from the card as they play, come in step 4): take card A out. The game pauses under "Card removed", asking for the card again; B and Menu do nothing. Insert card B: still waiting, "This isn't the SD card the game was started from". Take B out, insert A: "The game was saved", back to the library, and `ls -l` on the game's `.srm` and autosave shows them written just now. Launch the game again: it resumes where it was.
  4. Mid-game again, take the card out and choose Quit unsaved: back to the library with the message; nothing is written (`game: ended without saving`). Then a PS1 disc game, the same: Specular must not crash (a core touching the pulled card would end it with SIGBUS).
  5. A read-only card (the write-protect switch): the message stays above the library; changing a setting isn't saved (the file's time doesn't change); in a game, Save state says it can't, and quitting writes nothing.
  6. The kernel's read-only: with card A mounted, `mount -o remount,ro /mnt/SDCARD` over SSH, then change the volume. The log has `settings: …: Read-only file system`, then `wireless card … call "Recheck"`, `mount-card` runs (its log line), and the state becomes `read-only damaged`; the notice "The SD card has turned read-only" shows, then the message above the library. Take the card out and put it back to have it checked again.
  7. A repaired card: pull the card while a game writes (or set the FAT dirty bit on a PC with errors to fix): after reinserting, the repair message shows once above the library, with OK; it goes when pressed. Without pulling the card: over SSH, `sync; echo b > /proc/sysrq-trigger` restarts without unmounting, leaving the FAT dirty bit set, so the next start repairs the card. This also works on a Brick running from its SD card.
  8. On a Brick running from the SD card, pull it: the message ("the Brick turned off…") shows for the ~3 s before it powers off, also over a game.
- **Checking SSH on a release system on the Brick.** Turn on Developer details. (Until SSH is on there is no terminal: read the log afterwards in `/system/logs/messages`.)
  1. Settings shows "SSH" (off) and "Import SSH keys from the SD card" (0 SSH keys), with a note on where keys go. The log has `ssh: /usr/sbin/brick-ssh: exit status: 0, stdout "image=release\nssh=off\nkeys=0"`.
  2. Without `authorized_keys` at the card's root, Import says "Couldn't import SSH keys: no authorized_keys at the SD card's root", and the count stays.
  3. Put the PC's public key there as `authorized_keys` (e.g. with file transfer) and import: "Imported 1 SSH key", and the row says 1 SSH key.
  4. Switch SSH on: `ssh root@<address>` logs in. Restart the device: it is still on. Switch it off: new logins are refused.
  5. On a development system, Settings shows only "SSH is always on (a development system)."
- **Checking updates, the previous version and restoring on the Brick.** Run Specular in the foreground to see its log, with an SSH session for `brick-install slots` and `cat /etc/brick-version`. Each opening of Settings logs `install: offer {…}`, what the installer reported. The last step erases the installed system, so it comes last.
  1. In Crystaline OS, `make update-file`; put the file in `updates/` on the card, with an older update file and an empty file named `junk.update`. Settings → Updates: Version matches `/etc/brick-version`. Install update lists the newest file plainly and the older one marked Older (its "Install update?" says it is older than the running version); `junk.update` says why it can't be installed and can't be focused.
  2. Unplug the charger with the battery under 50 % and install the newest: "Update failed", with the battery's level, the hint to charge and the log's path; B goes back. Plug the charger in and install again: three steps, the screen can't be left, and the power button says to wait. Kill Specular (`kill <pid>`) during "Copying the update": once it is back, "Updating…" shows again and follows to the end. "Updated" → Restart: `/etc/brick-version` is the new version.
  3. Settings → Start previous version names the version from before; Switch, then Restart: the old version runs (`brick-install slots`). Do it again to get the new one back.
  4. On the installed system, with a backup on the card: Settings → Internal storage → Restore internal storage → the backup. Its question says the SD card is made to start the device; Restore: "Restore prepared" → Restart. The device starts from the card, and Specular asks "Restore the internal storage?", with the focus on Not now. Not now: Settings → Internal storage has Continue the prepared restore, and opening Settings doesn't ask again. Continue it and choose Cancel the restore → Restart: the device starts from the internal storage again.
  5. Prepare the restore again, restart, and choose Restore: "Restoring…" (sleep and power off wait) → "Restored" → Power off. Remove the card: TrimUI's system starts.
- **Measuring a scrolling list's cost on the Brick.** Put a few thousand games on the card for whichever system the Library lists first (empty files will do, e.g. `<title>.gba`; if the card also has Game Boy Color games, use `.gbc`, since that system is listed before the GBA), and turn on Frame statistics. Run Specular in the foreground with `SPECULAR_SCRIPT=a,down:6000,up:6000 SPECULAR_SCRIPT_MS=400`: it opens the system's games, holds down for 6 s, then up for 6 s, saves a screenshot and quits. Run `top -d 1` alongside. Each hold gets a `ui:` pair of its own. The down hold's should show about 350 frame times (370 on the desktop), 23 slots, 18 with rows, 6 on screen, and about 580–600 row slots changed (some 150 moves, 3 or 4 each). The CPU time per frame is the Brick's own: its median over 16.6 ms is the share of a core the UI thread takes while scrolling (37–40 % on 2026-10-19, 47 % before the fixes; docs/look-and-motion.md, Findings), and `top` should agree (BusyBox's `top` gives a share of all four cores together: 10 % there is 40 % of one). Row slots changed growing by about 23 a move mean every row near the view is laid out again at every move (docs/look-and-motion.md, Decisions).
- **Developer details** (a setting): shows developer-only settings, an icon gallery, the other network interfaces' IPv4 addresses (on the Wi-Fi screen, to find the device over USB), the installer's own reason why installing to internal storage, or preparing a restore from it, isn't possible, system versions in full (build time and commit, rather than the date), and why file transfer didn't start.
- **Keep Wi-Fi on** (a developer setting): stops WiFi Auto from turning WiFi off, so SSH over WiFi stays up.
- **Watchdog.** A core stuck on one frame for 6 s is reported, and Specular exits so the service manager restarts it.
- **Launch record.** `cache/launch.json` exists while a game runs. If Specular finds it at start-up (after a crash, the watchdog or a power cut), it logs it in full (`game: the last game didn't end; its launch record: …`), says which core stopped with which game, and removes it.
- **Seeing the Brick's screen.** `/dev/fb0` holds two 1024×768 BGRA buffers, one above the other; `/sys/class/graphics/fb0/pan` gives the one on show (`0,0` or `0,768`). `cat /dev/fb0` over SSH, then cut out that buffer (stride 4096 bytes) on the PC.

## Reproducing and testing

- **Unit and integration tests** (`cargo test`):
  - The app's behaviour: messages in, effects out.
  - Settings, the library and saves, using temporary folders.
  - List layout and held-button repeat.
  - The on-screen keyboard.
  - WiFi against a fake service socket replaying output recorded on a device.
  - Bluetooth parsing.
  - The SD card's state file: reading it, and following it as it is replaced.
  - The installer's progress protocol.
  - `brick-ssh`'s state and the WebDAV service's log lines, as the Brick reads them, and `brick-power`'s speed steps.
  - The CPU minimum's rules (`cpu::CpuMin`: the start level, what counts as a miss, steps up (the first to 1200 MHz) and never down, the config files' values), the pacer's timing of the vsync, and a game's minimum set, raised, and back to the default while paused and after it ends (with mGBA).
  - The lights and rumble effects, with plain events and times, and the rumble handed between threads.
  - The runtime, with real cores (mGBA, Nestopia, SwanStation) on generated ROMs (one mGBA ROM rumbles: it has Drill Dozer's game code and turns the cartridge's rumble pin on; a PS1 game on two discs changes disc and resumes on the second; a PS1 game calling a BIOS function OpenBIOS lacks is halted, and its autosave removed; a zipped Famicom Disk System game boots a BIOS of the tests' own), including whether a core's save states restore its save memory, that states made one after another (in one reused buffer) are each the game's own, and that a core autosaved at pauses is autosaved only when told and on quitting. This needs host builds of the cores (`make test` builds them); without them these tests are skipped. (The CPU minimum's handling of the frames after a save state is tested without a core.)
- **Wireless traces and scenarios.**
  - A wireless trace from a device converts into a scenario (`tools/trace-to-scenario.py`).
  - The desktop build replays a scenario (`SPECULAR_SCENARIO=<file>`): the same events, with the same answers and timing. A WiFi or Bluetooth problem seen on a device can be reproduced on the PC.
  - A default scenario is built in.
- **Driving the SD card's states on the desktop.** Either way, every state is traced (`wireless card …`), as on a device.
  - A state file you edit while it runs: `SPECULAR_CARD_STATE=/tmp/card/state` (its folder must exist; no file means a mounted card). Write it in the system's format (docs/sd-card.md), e.g. `printf 'absent\nNo SD card.\n' > /tmp/card/state`, then `printf 'mounted\n\ncard=aaaa check=repaired\n' > /tmp/card/state`. Changing `card=` between two mounted states is another card.
  - A scenario: a `"card"` script in `SPECULAR_SCENARIO`'s file, whose events are the card's states (`{"status": "Absent", "message": "…", "id": "aaaa", "check": "clean"}`; reason and check as in the state file) and whose answer to `"Recheck"` is what the system then reports. With `SPECULAR_SCRIPT`, this drives a game whose card goes and comes back without hands: e.g. `{"card": {"start": [{"event": {"status": "Mounted", "id": "aaaa"}}, {"after_ms": 5000, "event": {"status": "Absent"}}, {"after_ms": 9000, "event": {"status": "Mounted", "id": "aaaa"}}]}}` with `SPECULAR_SCRIPT=a,a,volup,volup,volup,volup,volup,volup,volup,volup SPECULAR_SCRIPT_MS=1000` launches the first game, pauses it at 5 s and saves it at 9 s (the volume presses only keep the script going past 9 s: it quits after its last press).
  - A write refused as read-only, for real: run Specular in a user namespace whose data folder is a bind mount, and remount it read-only while it runs. With `SPECULAR_CARD_STATE`, the desktop's recheck then reports `read-only damaged`, as `mount-card` would:
    ```
    unshare -rm sh -c 'mount --bind sdcard sdcard; SPECULAR_CARD_STATE=/tmp/card/state specular sdcard & sleep 5; mount -o remount,bind,ro sdcard; wait'
    ```
    Change the volume after the remount: the settings' write fails, and the recheck follows.
- **Scripted input and screenshots.**
  - `SPECULAR_SCRIPT=down,a,…` plays a list of button presses into the app, one every `SPECULAR_SCRIPT_MS` (default 400). `down:6000` holds the button for 6 s, repeating as if held.
  - It then saves a screenshot (raw RGBA) to `SPECULAR_SNAPSHOT` and quits.
  - This is the basis for end-to-end checks; there is no test runner around it yet.
- **Benchmarks.** Ignored tests time focus moves in a 3,000-game list and a search of 3,000 titles (`cargo test --release -- --ignored --nocapture`).

## Measuring and exploring

These are cargo examples. Build them for a device and run them there through Crystaline OS: `make specular` puts them in its `build/specular/aarch64-unknown-linux-gnu/release/examples/`, and `tools/run-specular.sh <binary> [args]` runs one.

- **Headless player** (`specular-runtime`'s `play`). Runs a core and a ROM with no UI, optionally paced by vsync. It reports the core's time per frame and can save the last frame. `-o key=value` sets a core option (use Specular's defaults, its `CoreDecl::defaults`, e.g. `-o nestopia_blargg_ntsc_filter=disabled`); `SPECULAR_BIOS` is its `bios/` folder. Every environment call the core makes that Specular refuses is logged once, with its number.
  - On the Brick, a core's speed depends on the CPU's, which the `ondemand` governor keeps low for a game paced by the vsync (docs/runtime.md, Findings). `brick-power` (no arguments) shows the speed during a run. To compare at one speed: write `performance` to each `/sys/devices/system/cpu/cpufreq/policy*/scaling_governor`, then the speed to `policy0/scaling_max_freq`. To undo: write `ondemand` back to each `scaling_governor`, then run `brick-power profile balanced`, which restores the speed range and `ondemand`'s sampling interval but not the governor (switching governors resets the interval to 2 s, so the order matters).
  - A 60 s run (`play --vsync … 60`) at full speed gives 3,612 frames (60.2 fps). A game's opening varies in load, so compare runs of the same length.
- **Device measurements** (`devices/brick/examples/s*`). Each measures one part of the stack on a device:
  - Toolchain.
  - Slint on the device's GPU.
  - Frames handed from another thread.
  - Display timing.
- **Input injection** (`inject`). Writes button presses into a device's input, to drive a running Specular remotely. On the Brick, padbridge re-reports its own state after each write, so a d-pad hold ends early and a switch written there (the FN switch, `SW_TABLET_MODE`) lasts only until padbridge's next report. For holds, use `SPECULAR_SCRIPT` (Reproducing and testing).
- **WiFi and Bluetooth consoles** (`specular-linux`'s `wifi` and `bluetooth`). An interactive WiFi console, and a scripted Bluetooth session with a test tone. Both talk to the real services on a device.

## Data

- **Game identification tables** are generated from a pinned libretro-database commit (`tools/trim-db.py`). They are compiled in.
- **Core option lists** (`data/cores/<core>.json`): what each core `tools/build-cores.sh` builds declares, compiled into Specular as its options' settings and as constants (see docs/settings.md). `make cores` (for this PC) loads each core it built and rewrites a list only if it changed; commit the change with the core's update. The `core-options` example does that alone (`cargo run -p specular-runtime --example core-options -- data/cores target/cores/host/*.so`). A test fails if a list differs from the core built for this PC, and one if a core built has no list. A new core needs its list before its `CoreDecl` can name it (`options: <core>::LIST`): build it, run `make cores`, then add the `CoreDecl`.
- **Credits** are worked out by each device's build script (`crates/specular-credits`), from the crates it links and `data/credits.tsv` (what isn't a crate; its header explains it). A new core in `tools/build-cores.sh` needs a line there, or the build fails. A build warning (`credits:`) names any crate that ships no licence text, and what to add. The licence texts are written to `licences.txt` beside the binary (`target/<profile>/`).
